## 0. Why this revision exists — root cause, verified with real evidence, not assumed

**Client's complaint (2026-09-07):** the UI does not match why.com's format, and search results are not good enough. Client is threatening to cancel the project.

**Investigation done before writing this plan (2026-09-07):**

1. **Took real screenshots of the actual, live, JS-rendered why.com** (not just guessed from earlier documentation) — a plain fetch only returns the SPA's raw markup shell, not the real rendered design, so a headless-Chrome screenshot was required to see the truth. Confirmed why.com is:
   - **Dark-mode only, pure near-black background** (`#000`-ish), gold/amber accent, serif display font on dark
   - **Rotating single headline question** ("Why are women's sports suddenly attracting record investment?") with **3 pill-shaped category tabs** (Sport / Technology / Politics) above the fold — not a static search bar with example chips
   - Clicking "Ask WHY." reveals a **full-pill rounded search bar** with a magnifying-glass icon on the left and a light cream circular submit button (inverted from the dark page) — a very different shape/interaction than a plain rectangular input
   - Minimal nav — no visible persistent links, everything behind a hamburger icon
   - "Ask WHY." / "WHY. Pro" as small underlined text tabs beneath the headline

2. **Took real screenshots of our own current live site, in both dark and light mode.** Found a critical, real explanation for the disconnect: **the app defaults to `system` theme preference** (`providers.tsx`: `defaultTheme="system"`). In dark mode, our site already looks reasonably close to why.com's tone (dark background, serif headline, centered search). **But in light mode — which is what most users, and very likely the client, see by default — the site is a completely different cream/off-white, orange-accented theme that looks nothing like why.com.** This is almost certainly the real, concrete reason the client feels the UI doesn't match: they are very likely judging the light-mode version against why.com's dark-only design.

3. **Confirmed our current top-of-page interaction pattern is structurally different from why.com's**, independent of color: we show a static search bar with 4 always-visible example-question chips below it; why.com shows one rotating headline question plus 3 category filter pills, with the actual search input hidden behind a separate "Ask WHY." action. These are two different product concepts on the same page, not just a color/skin difference.

**Conclusion:** this is not a case of "needs more polish" (Revision 2's UI pass, while a real improvement, did not address either of these two structural gaps). This is a genuine mismatch in default visual mode and top-of-page interaction pattern versus the actual reference site the client asked to be copied. The plan below fixes both, plus independently re-verifies the second complaint (result quality) with fresh evidence rather than assuming Revision 2's verification still holds.

## Step 5 — Independently re-verify search RESULT quality (the client's second, separate complaint)

**Problem:** the client said results are "not good as expected," separate from the UI complaint. Revision 2 already verified RAG answers against the real database and got strong results (see `AgentGuide/revision2.md`) — but that verification is now several days old, and the client's fresh complaint means it needs re-confirming with new evidence, not assumed still valid, and specifically needs to check whether anything regressed or whether the client's actual test queries expose a real gap not caught before.

**Fix (investigation-first, no code change assumed yet):**
- Re-run the full RAG pipeline against a fresh, larger batch of realistic public-safety questions across multiple US cities/regions (not just NYC, since the client explicitly said "users all around the United States")
- **This directly surfaces a real, known, and currently true limitation: the ingested dataset is NYC-only** (`app/services/ingestion/nyc_socrata.py`, 400 records, NYPD complaint/arrest data only). A user asking about Chicago, LA, or any non-NYC city will correctly get the honest "no live/verified data for this" response — which is *correct, intended behavior* per the system design, but may be exactly what the client is perceiving as "results are not good," if they're testing with non-NYC questions and expecting real data back.
- Confirm this hypothesis directly: test both NYC questions (should return real cited data) and non-NYC questions (will honestly decline) and present both outcomes clearly, since the fix here may not be a code bug at all but a scope/expectation conversation — the client's own words ("users all around the United States") suggest they expect multi-city coverage that was never built (NYC was the explicitly agreed starting city per the original revision2.md chat log, with "more cities added along the line").

**Test:**
- [x] Batch of 8 real test queries across NYC, Chicago, LA, Houston, Miami, and a generic US-wide question, with real transcripts saved
- [x] Each NYC-scoped answer cross-checked against the real database (same method as prior verification)
- [x] Each non-NYC answer confirmed to honestly decline rather than fabricate
- [x] Clear written summary of findings — is this a code defect, or a scope/coverage gap that needs a client conversation about expanding beyond NYC?

**Result — a real, confirmed CODE DEFECT was found, not a scope/coverage gap:**

The first full batch (all 8 questions, NYC and non-NYC alike) came back with **zero real cited data on every single query**, including "Was there a felony assault reported in Staten Island?" — a question already verified in an earlier session to return a real, cited NYPD record. This ruled out the original "NYC-only coverage" hypothesis immediately: even in-scope NYC questions were failing.

**Root cause, traced to the actual source:** `find_relevant_records()` (`vector_search_service.py`) was throwing `psycopg2.errors.UndefinedColumn: column public_records.city does not exist` on every call. `search_service.py`'s `stream_answer()` catches this exception and silently degrades to the generic "I don't have real-time access" no-records path (by design, so a retrieval failure never 500s the whole search) — which is exactly the flat, uncited, generic-sounding answer the client is calling "not good."

Traced further: this project has no Alembic migrations — schema is managed only via `SQLModel.metadata.create_all()`, which creates missing tables but never alters existing ones. The `PublicRecord` model's `city` column (and the ingestion code in `nyc_socrata.py`, which already correctly writes `city="New York City"`) were both already correct — but the **live Postgres table still had the old column name `state`** (holding `'NY'` for all 400 rows) from before that field was renamed in the model. The rename was never applied to the live table, so retrieval has been silently broken since that change shipped — for NYC and non-NYC queries alike.

**Fix applied:** `ALTER TABLE public_records RENAME COLUMN state TO city` (run directly against the live DB after explicit confirmation, since this is a production data change). Verified immediately after:
- Staten Island felony assault → **5 real relevant records retrieved**, e.g. "Felony complaint: FELONY ASSAULT (STRANGULATION 1ST) reported in STATEN ISLAND, precinct 121..."
- Bronx drug arrests → **5 real relevant records retrieved**, e.g. "F arrest: DANGEROUS DRUGS (CONTROLLED SUBSTANCE,POSSESS.) in the Bronx, precinct 44, on 2026-03-11."
- Chicago curfew → **0 records retrieved**, correctly and honestly (no fabricated Chicago data)
- LA robbery → retrieval returned 5 NYC Brooklyn/Queens robbery records as semantically-similar-but-wrong-city matches (a secondary, minor finding: the similarity threshold checks offense-type text only, not location) — **but the LLM already self-corrects this correctly end-to-end**, per the existing `RAG_RECORDS_INSTRUCTION`'s explicit "say so plainly" guidance: the real streamed answer said *"I don't have any Los Angeles robbery reports... those are not Los Angeles incidents"* and pointed the user to the LAPD's real data source instead of fabricating a match. No code change needed here — this is the system working as designed.

**Conclusion:** this was a genuine, product-wide regression bug (broken RAG retrieval on every query, not just non-NYC ones), now fixed and verified with real before/after evidence. It is NOT a scope/coverage gap — the "users all around the United States" question from Open Item #2 below is still real and separate, but it is no longer entangled with a bug that was silently breaking even the in-scope NYC answers the client should have been seeing correctly all along.

## Step 9 — Nationwide data coverage, built and verified city-by-city, one phase at a time

**Why this exists:** the client's original complaint ("users all around the United States... you are unable to achieve this... you can easily use AI to help you but you don't") is a real scope gap, not a bug — confirmed via real research (2026-09-08) that there is no free, real-time, individual-record, nationwide police API. This is genuine, replicable integration work: most major US cities publish their own open crime/arrest data (mostly via Socrata, same platform as NYC's existing pipeline), but coverage drops off fast outside the largest ~30-50 metros, and roughly 18,000 smaller US police agencies publish nothing structured at all. The plan is to maximize real, honest coverage of major-population cities in verified phases, exactly like the UI steps: each phase built, tested with real ingested data and real query verification, before starting the next — never silently expanding scope without re-verifying quality.

**Research findings (full detail, sources logged 2026-09-08):**
- Cities confirmed to have real, free, no-auth, incident-level open data similar to NYC's: **NYC (done), Chicago, Los Angeles, Philadelphia, Phoenix, Dallas, Austin, Seattle** — mostly Socrata (SODA API), a couple on custom/CKAN portals but still free and machine-readable.
- Weaker/partial: Houston (less granular, historically PDF-heavy), San Antonio (90-day rolling window on some feeds, separate NIBRS bulk downloads needed for depth), San Diego (portal still maturing as of 2024-25).
- FBI NIBRS is the only genuinely nationwide source but is NOT equivalent to "search police records": annual-cadence, de-identified, aggregated (no case-level detail, no addresses), and participation is uneven — big states like CA/TX/FL/NY/PA are actually among the weakest NIBRS reporters.
- `OpenPoliceData` (open-source Python library) already aggregates 550+ datasets across 236 agencies + 11 full states — a candidate ingestion accelerant for later phases instead of hand-building every connector from scratch.
- Commercial aggregators (SpotCrime, CrimeMapping) exist but are paid for API/commercial use (~$199/mo+) and are shallower "incident pin" data, not full reports — not a substitute for real integration, flagged as a possible future supplement only.

## UI audit — 3 real issues found and fixed

Per an explicit "fix all the UI issues" request. **1. Real, user-visible bug — SearchBar's landing-page input text was nearly invisible.** The pill deliberately uses a fixed, near-black semi-transparent fill (`rgba(17,17,16,0.86)`) to match why.com's own live-measured search bar — a real, intentional, previously-undocumented deviation from §4.3's baseline `--bg-elevated` spec, not a mistake to revert. This was the one place that had regressed to the banned pairing. **Fixed** by switching the label to `text-text-primary` (border stays `accent` — borders only need the 3:1 UI-component threshold, which accent clears).

**3. Minor token drift — an arbitrary pixel size instead of the established scale.** `SessionCard.tsx`'s "Deep search" badge used a bespoke `text-[11px] leading-4` instead of the `text-caption` token (0.75rem) every other badge in the codebase already uses for this exact visual role. **Fixed** by switching to `text-caption font-medium`, matching the established pattern.

**Also introduced, per the guideline's own §11 rule** ("propose new token explicitly" rather than hardcode): a `--text-search-pill` (1.25rem) token for the input's real, live-measured 20px why.com-matching size, which had also been a raw `text-[20px]` arbitrary value — named as its own scale entry (not force-fit to the nearest existing size, `body-lg` = 18px, a real but different value) so the why.com-matching intent stays traceable.

**Verified for real, not assumed**: a genuine production build (`next build`) completed cleanly (compiled, typechecked, all 19 routes generated), lint passed with zero warnings, and — critically — directly inspected the actual generated production CSS output to confirm both new custom tokens produced real, correct utility classes (`text-search-pill{font-size:1.25rem;...}`, `text-search-pill-foreground{color:var(--wp-search-pill-foreground)}`), not just assumed Tailwind's CSS-first `@theme inline` convention would pick them up the same way existing tokens do.
